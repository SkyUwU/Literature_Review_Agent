# 依計畫執行

將已授權計畫完成為可審閱的結果。必要測試與交接屬於實作的一部分，不用另外要求相同授權。

## 接續計畫

- 依適用的 AGENTS.md 與使用者指示，核對工作目錄、Git 變更、指定交接摘要及權威計畫。確認目標、範圍、驗收與未決問題，保留使用者變更。
- 簡短說明本輪範圍。已有「依此計畫執行」等授權就繼續；名稱、函式拆分等例行選擇自行處理。
- 若現況使計畫需要改變範圍、公開介面、品質政策、資料保存或外部費用，先說明差異並釐清；只暫停依賴該決策的工作。
- 定位必要程式與測試片段，按依賴順序修改。不以大量試改／試跑取代尚未釐清的關鍵設計，也不無理由重讀全部資料。

## 執行命令前

遵循專案的 runtime 和常用命令；uv 專案通常使用 `uv run python ...`，不把某個 runtime 選項寫成通用要求。

針對實際命令檢查啟動、setup/teardown 和相關依賴的副作用：是否清空／覆寫資料、載入 dotenv、選用真實 client、下載模型或連線。Fake-client 或 dry-run 的名稱不能代替這項確認。

隔離方式按測試需求選擇，例如暫存輸出目錄、注入路徑、獨立暫存 cwd 或最小 fixture；不用一律改 cwd。所有可能被重建的路徑均須指向隔離資料，仍須確認程式沒有使用指向真實資料的絕對路徑。變更 cwd／環境後用 finally 或 cleanup 還原。

離線驗收需避免載入使用者 secrets，注入必要的 fake client／encoder，並用有效的網路隔離攔截意外連線。不能只清空一個環境變數就假設所有設定來源都停用；也不能只改一個 socket 方法就宣稱所有外部操作都被封鎖。

已授權的真實整合驗證依計畫、provider 用量及專案規則執行；不以離線規則阻擋它。遇到權限限制走正常申請流程，拒絕後不更換工具繞過。無法確保命令副作用在授權範圍內時，先完成隔離或提出具體問題。

## 修改與驗收

1. 完成需求所需的修改，保留計畫要求的相容性與品質門檻；重用適當 fixture，新增能驗證需求和重要邊界的測試。
2. 先跑新增測試與直接受影響的驗收。簡單可逆修改可以只做必要檢查；專案要求的檢查仍須完成。
3. 失敗時先判斷是實作、fixture、環境或契約問題。若要稱為既有失敗，須有可核對依據；沒有依據就標示未釐清。
4. 修正後重跑受影響部分。有新修改、失敗或未解疑慮時才擴大／重複驗證；計畫、專案要求或影響範圍需要時執行完整 suite。通過必要驗收後停止。
5. 審核 final diff，確認需求完成、使用者變更保留，並完成專案要求的 hygiene checks。排除測試時明列名稱、理由與驗證缺口；不能排除新失敗後宣稱全數通過。

保留成功／失敗結論、測試名稱與必要 traceback。詳盡 log 按專案慣例保存，不將冗長成功輸出反覆注入對話。工具尚未完成時先取得完成狀態，再依結果決定下一步。

## 完成、阻礙與事故

達到計畫驗收後交付，不順手增加無關功能。API 呼叫、依賴安裝或提交若已在明確授權內，依授權執行；未獲授權的外部操作不因 skill 啟用而自動取得權限。

發現資料意外受影響時，立即停止可能加重損害的操作，說明已知影響與不確定性，只做可核對且在授權內的恢復。不能補造資料或隱瞞恢復限制。

有阻礙時留下可審閱的進度，指出缺少的資訊或權限，不持續盲目重跑。交付實際變更、驗收結果、未完成項與限制；hygiene、mock、完整 suite 和真實服務驗證分開描述。提交命令若需提供，明列本輪檔案，不混入其他修改。

只使用本輪實際可用且獲准的工具／代理；自己完成審核就稱自審。Skill 提供操作指引，不取代執行環境的檔案與網路隔離。
