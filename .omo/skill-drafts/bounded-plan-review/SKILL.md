# 撰寫與審核計畫

產生符合使用者需求、能讓下一輪直接接續的計畫。篇幅依任務調整；簡單修改可用短清單，不強迫套用大量章節。

## 先確認需求與現況

- 依適用的 AGENTS.md 與使用者指示，確認工作目錄、Git 變更及指定交接資料；保留既有變更。
- 用 rg 定位相關入口、介面和測試，再讀必要片段。只有歷史決策會影響本題時才查相關紀錄，不反覆讀整份檔案或所有歷史。
- 區分目前核對的事實、歷史紀錄及推測。舊測試通過、檔案曾存在或某工具曾可用，不能直接當作本輪事實。
- 會改變需求、公開介面、品質政策、資料保存或外部費用的未決問題，先釐清。名稱、函式拆分等不改變結果的實作細節，可提出合理預設，不必逐項詢問。

## 寫出可接續的計畫

依複雜度交代以下內容；不相關的項目可省略：

1. **目標與範圍**：要解決的問題、可觀察的完成結果、涵蓋與排除項目。
2. **主要設計**：預計影響的檔案／介面與相容性。跨階段工作須說明資料、狀態、例外與保存責任；不要留下需要實作時猜測的關鍵決策。
3. **執行順序**：有依賴的修改先後，以及正常和必要失敗路徑。
4. **驗收**：需求對應的觀察結果與必要測試。會執行命令時，說明環境、輸入輸出和已知副作用；只有可能碰觸真實資料、秘密或服務時才安排相應隔離。
5. **未決問題**：分列阻擋實作的問題、可接受的假設、非阻擋建議及驗證限制。

任務範圍可以包含多個必要子步驟；不要把無關改善包進計畫，也不要為符合「單一里程碑」而把完整需求切到無法驗收。

## 審核並修正

對照需求和已核對的程式檢查：範圍是否適當、介面是否存在、責任是否一致、品質門檻是否保留、驗收是否真正測到需求，以及命令是否可能覆寫資料或意外連線。

檢查可否重用現有測試、減少無理由的完整 suite 或大規模讀檔。省成本不能取代必要驗收，也不能靠放寬契約讓結果通過。

每個會影響實作的發現，附上依據、影響和修改方式；修正後只重新檢查受影響部分及必要的整體一致性。尚未排除的關鍵問題，不能標為可執行。

審核結論使用以下任一種：

- **可執行**：重要決策清楚；列出仍需遵守的假設與驗證限制。
- **需釐清**：列出阻擋問題、原因與可選方案；非阻擋建議分開列。

## 交付界線

遵守專案對計畫保存的規則。只要求討論時在聊天交付；已有保存授權時寫入指定位置。計畫結論須帶上範圍、驗收及未決問題，讓執行者不必重新猜測。

審核通過不等於獲准實作；已有實作授權也不必再要求相同確認。此 skill 不自行轉入程式修改、測試或安裝。

若使用者已要求「先規劃審核，再直接實作」，完成審核後按既有授權切換到執行階段，不因使用此 skill 而額外要求確認。

審核方式依使用者授權、專案規則及本輪實際工具決定。自己審核就稱自審；只有實際使用其他審核者時才稱獨立審核，不套用其他環境的流程名稱。
